# 图灵审讯：首版交付计划

日期：2026-10-24。状态：用户已确定玩法方向；规则、架构和平台接入尚待设计与验证。本文件中的 T 编号是计划任务编号，不是已创建的 GitHub Issue 编号。

## 1. 已确认范围

单玩家、单 AI 审讯官、一个预置案件，按住说话，目标局长约 3–5 分钟。核心循环：玩家陈述 → AI 追问并调证据 → 展示有来源的矛盾和嫌疑值 → 生成可解释的结案报告。

首版支持无辜者与真凶两种身份的设计与验收。具体胜负条件、分数、阶段推进和时长上限在 T02 固定；外部骨架中的 50 分起点、70 分阈值不自动沿用。

多人、多案件、音色复刻、可切换情绪按钮不列入首版。采用一个固定可用音色。打断能力是否进入承诺范围由 T03 实测后确定。

## 3. 里程碑与依赖

- M0 项目有规则：T01 完成。可以发布设计类 Issue。
- M1 设计可落地：T02–T05 完成。玩法、接入路线、接口和验收都可供审查，才进入 T06。
- M2 最小闭环：T06–T10 完成。自有网页能通过真实平台完成一局。
- M3 首版可交付：T11–T12 完成。测试、实测、部署说明和版本证据齐全。

T02 与 T03 可同时推进；T07/T08 与 T09 可在契约确定后分别推进。本计划不预设多人或多 Agent 执行。

不沿用原材料的两天承诺。T03 完成后，根据接入问题和已冻结范围估算工时，再排日历。账号或平台能力阻塞时记录具体原因和可推进的独立任务，不以模拟结果关闭集成任务。

## 4. 骨架的边界

骨架服务于验证工程能启动、能检查、能扩展。T04 确定语言和框架后，再创建真实需要的目录和文件。

建议职责划分：后端的规则、接口、平台适配；前端的语音、游戏状态展示；测试的规则、契约、端到端。职责可以对应少量文件，不要求每项单独建包。

骨架包含：依赖与锁文件、启动入口、健康检查、基础页面、配置示例、忽略规则、基础检查和 CI。不得用大量空类、空接口、返回假成功的工具函数填充目录。尚未实现的功能应明确不可用。外部骨架在相关任务内按契约逐项评估复用。

## 5. 测试与验收基线

以下作为 T05 的初始门槛，若需调整须在设计记录中说明理由，不能为让失败的实现过关临时降低。

- 自有后端业务代码行覆盖率 ≥80%；核心规则模块分支覆盖率 ≥90%。报告列出统计范围和排除项；第三方库、生成物不计入，不排除难测业务代码。
- 无论覆盖率多少，非法迁移、分数上下界、无来源矛盾、重复调用、结案后写入、跨局污染和身份泄漏都要有明确测试。
- 前端对语音生命周期和状态同步编写行为测试，并验证完整用户流程；不为静态样式编写凑覆盖率的测试。
- 模拟平台测试在普通 CI 中运行；真实平台测试单独执行，记录配置版本和证据。普通 CI 通过不代表平台集成通过。
- 延迟指标应定义测量起止点、测试环境和样本量。T03 测基线、T05 固定门槛、T11/T12 对照验收，不能只写“低延迟”。
- 阻断缺陷包括：无法完成一局、跨局污染、重复扣分、无来源判罚、身份提前泄漏、报告与状态矛盾，以及无法恢复或明确结束的连接故障。

验收用例格式：AC 编号 / REQ 编号 / 前置条件 / 操作步骤 / 预期结果 / 自动或人工 / 实际结果 / 证据 / 版本。未执行标记“未执行”，不能填“通过”。

## 2026-10-24 执行调整：个人开发快速落地

用户要求仅重要部分走 PR。以上 T01–T12 保留为检查清单，不再要求一任务一 Issue/PR，也不再要求所有小改走分支。

实际按三个里程碑推进：
1. 可玩剧本预览：简版需求/架构/验收、最小工程、规则、界面及自动测试合并为一个重要功能 PR。明确是预置回答的剧本试玩，不假装真实 AI 或语音接通。
2. 灵矽真实接入：完成账号/设备、语音、工具与会话关联的实测，独立重要 PR。接入假设未验证前不写猜测性适配代码。
3. 联调交付：稳定性、真实端到端验收；小修直接提交，规则或契约变化走 PR。

原型允许先于平台验证交付，但平台接入任务及首版完成状态仍保持未完成。详细设计只写当前实现需要的内容，后续以实测补齐。
