## 可以带入方案讨论的判断

以下是根据已有材料做出的工程判断，不是竞品事实核查结果：

- 优先评估单玩家、单 AI 角色、预置内容、短局闭环。它可以减少角色编排和联网同步工作。
- 语音应参与核心玩法：提问、回答、追问和反馈，而不只是给文本配音。
- 先验证真实语音与工具链，再估算完整开发工期。前后端代码少不等于集成风险低。
- 游戏状态和分数应由服务端规则维护。LLM 提出语义判断，后端检查引用、参数和状态；确定性计分不能保证语义判断正确。
- 先明确一局如何开始、如何推进、如何结束、玩家为何获胜，再添加音色复刻、情绪切换和报告美化。

## 历史选题比较（主游戏已是「谁是人类」，下表只作记录）

下表是早期候选。办事闯关后来让位给备用游戏「你是什么人类模型？」；当前主游戏见 [docs/architecture.md](../architecture.md)。

| 方向 | 核心循环 | 需要先回答的问题 |
|---|---|---|
| AI 审讯玩家（外部方案名“图灵审讯”） | 玩家陈述 → AI 追问与调证据 → 对质 → 结案 | 无辜者和真凶的体验是否公平？如何拒绝无来源的矛盾？ |
| 单 AI 主持海龟汤 | 固定谜题 → 语音问答 → 提示 → 还原答案 | 主持人如何不泄底？模糊问题和答案如何判定？ |
| 语音角色挑战与赛后报告 | 给定任务 → 对话挑战 → 规则评价 → 报告 | 评分是否可解释？是否具备游戏目标而非只有聊天？ |

暂不纳入首版讨论范围的扩展：完整语音狼人杀、真人多人房、多案件平台、开放世界。若后续确有需求，再评估，不提前建设。

“单人、两天、必须使用灵矽”来自外部材料，需要结合赛事规则和实际投入时间确认；不能直接作为已确认排期。

## 平台验证清单

下表是最初提出的验证清单。最新实际结果见上方真实平台验证记录；不能用本地模拟通过替代真实平台验证。

| 编号 | 验证事项 | 通过证据 | 对方案的影响 |
|---|---|---|---|
| V01 | 账号、模型、音色、额度及赛事要求 | 当前控制台配置与赛事规则记录 | 确认可使用能力和硬约束 |
| V02 | 自有浏览器客户端鉴权与连接 | 真实建连、握手和断开日志；不记录令牌 | 决定直连或服务端代理，不能猜 query 参数代替请求头 |
| V03 | 上下行音频格式与帧参数 | 协商记录及真实录音、识别、播放结果 | 决定编码解码实现；PCM 支持不能靠假设 |
| V04 | MCP 传输与工具调用 | 平台真实发现工具、调用并收到结果的日志 | 决定采用的协议及 SDK；不提前手写协议 |
| V05 | 按住说话、打断及播放队列 | 浏览器实测录像与时间记录 | 确定交互方式和延迟验收阈值 |
| V06 | 会话、设备与游戏局的绑定 | 两次连续开局与延迟工具调用测试 | 防止上一局调用改动下一局；单玩家也需要生命周期边界 |
| V07 | 音色与情绪控制能力 | 所选模型和音色上的实测记录 | 决定是否纳入首版，不能承诺任意情绪按钮 |

## 从调研转入正式设计的条件

1. 选定一个玩法，写清玩家目标、输入、反馈、胜负条件及最小范围。
2. 记录关键能力验证结果。尚未通过的能力必须有明确处置，不把双屏控制台演示写成自有 Web 客户端已接通。
3. 需求文档用可观察行为描述功能；架构文档定义状态所有权、会话绑定、接口、错误处理和部署边界。
4. 测试方案区分规则单测、接口/工具契约测试、真实平台集成测试和人工体验验收。
5. 验收用例对应需求编号，写明前置条件、操作、预期结果、证据和通过状态；延迟指标先测基线再定阈值。
6. PR 围绕可验证的小目标拆分，每个 PR 说明改动目的、关联需求、验证结果及未解决问题。

覆盖率不能等同于语音链路可用或玩法可靠。当前门槛、统计范围、执行命令和测量结果以根README及验证记录为准；重复调用、非法阶段、分数边界、结案后写入、跨局污染等关键用例须明确覆盖。
